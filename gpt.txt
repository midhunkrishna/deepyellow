Yes. And I think your idea of shipping a small SQLite database containing file characteristics is a very good starting point.

What you're describing is essentially a file relevance and deletion-risk prediction engine. It would analyze files using their metadata, context, and relationships to other files, then recommend what users can remove to reclaim storage.

The key is that I wouldn't start with machine learning. I'd build a hybrid system combining a curated knowledge base, heuristic scoring, and eventually a lightweight learned model.
1. The fundamental distinction

There are three different questions your application needs to answer:

    Is this file safe to delete? Will deleting it damage the OS, an application, or the user's work?

    Is this file relevant to the user? Is the user likely to want it again?

    How much space will deleting it actually reclaim?

These are independent dimensions.

Notice something important: file extensions alone cannot tell you whether a file is safe to delete.

A .sqlite file might be a disposable cache or the only database containing years of user information.

You need to understand the file's role, not just its type.

6. Recommendation categories

I'd avoid automatically deleting anything until your app has demonstrated high precision.

Regenerable cleanup

Verified caches, temporary build artifacts and other disposable data, subject to application-specific safety checks. Potentially eligible for one-click cleanup.

Recommended review

Old installers, downloaded archives and verified duplicate files. User confirmation required.

Inspect manually

Old documents, large media collections and inactive project folders. Show size and context, but don't presume they are disposable.

Protected

OS files, application state, unknown databases, active projects, cloud-managed data and anything with unresolved dependency or permission concerns.

For macOS specifically, Apple's file resource APIs expose useful information such as allocated size, whether a file is purgeable, and whether files may share content. These can help classification and storage estimation, but don't establish a general license to delete user data. 
Apple Developer Documentation+1

Use the OS Trash mechanism where practical, rather than permanently removing files. macOS exposes FileManager.trashItem(at:resultingItemURL:) for this.

7. What about machine learning?

Once your rule-based system is working, this becomes an interesting supervised-learning problem.

You can collect feedback such as:

    User accepted a deletion recommendation.

    User dismissed it.

    User marked a directory as important.

    User repeatedly retained certain file categories.

    User restored a trashed file.

Store this in a separate local SQLite database, along with inventory and recommendation history. Keep the shipped knowledge base independently versioned and updatable.

Eventually, you can train a small model such as gradient-boosted trees or logistic regression to predict whether a user will accept a cleanup recommendation.

That is a much more measurable target than trying to train a model to predict whether a file is objectively important.

You could train offline and ship the model for local inference, without uploading private filenames or file contents. Importantly, deletion actions should remain subject to deterministic safety policies regardless of what the model predicts.
8. How I would scope the MVP

I'd implement it in this order:

    Build a filesystem scanner collecting file type, path, logical and allocated size, timestamps, and filesystem attributes.

    Ship a curated SQLite catalog of 30–50 well-understood artifact patterns for your target OS.

    Implement a deterministic protection layer with explicit allowlists and denylists.

    Add relevance scoring for user-review candidates.

    Build duplicate detection using size grouping followed by cryptographic hashing, with care for hard links and filesystem clones.

    Add an explainable recommendation interface and collect user feedback.

One design detail I'd emphasize: build high precision before broad coverage. Failing to recommend 10 GB of removable files is frustrating. Recommending the deletion of one irreplaceable database could destroy trust in the entire application.

Also, a file's logical size isn't necessarily the storage you'll recover. Hard links, copy-on-write clones, sparse files and snapshots can make estimated savings inaccurate.
My recommendation

I would create two engines, not one:

Engine A — Known Artifact Classifier: Powered by your versioned SQLite knowledge base. Its job is to recognize known, regenerable or disposable files with strong evidence.

Engine B — Personal Relevance Estimator: Powered initially by metadata heuristics and eventually by learned user preferences. Its job is to rank files for manual review, never to authorize deletion independently.

This separation makes the system safer, testable, and extensible.

One important question: Are you building this primarily for macOS, Windows, or both? The architecture remains similar, but the available metadata, OS protection mechanisms, and knowledge-base rules differ substantially.

For example, they won't reliably tell you that Downloads/report-final.pdf is unimportant just because it hasn't been modified in three years.

That prediction still requires your own relevance model and user feedback.

I see. What do you mean by relevance model?

By relevance model, I mean a system that predicts how likely a user is to need or care about a file in the future, based on its metadata and context.

It's different from a cleanup-rule database.

    Cleanup rules: Is this file technically safe to remove?

    Relevance model: Is this file important enough that the user would want to keep it?

For your macOS app, I'd use both.

4. Where machine learning becomes useful

The interesting next step is personalization.

Imagine two users:

User A: Software engineer. Regularly downloads installers, generates build artifacts, and accumulates temporary project files.

User B: Photographer. Downloads large images, edits them infrequently, and keeps old originals.

The same file metadata may have very different meanings to these users.

You could learn from explicit user feedback:

    User approves a suggested cleanup.

    User chooses Keep.

    User marks an entire folder as important.

    User restores something from Trash.

After accumulating enough feedback, you could train a lightweight model (such as logistic regression or gradient-boosted trees) to estimate the likelihood that a user would accept a recommendation.

This could run entirely on-device.

6. What I'd recommend for your MVP

I would not build a predictive ML model yet.

Instead, implement:

    A SQLite knowledge base describing macOS file categories and known disposable artifacts.

    A deterministic relevance scorer using location, type, age, and context.

    A protection engine that blocks dangerous recommendations.

    A feedback mechanism that records what users keep or remove.

The most interesting longer-term question is whether the system can learn personal relevance without examining file contents.

That's a valuable differentiator for a privacy-first Mac cleanup app.

One thing I'd challenge, though: rather than immediately trying to predict relevance for every file on the disk, start by ranking large files in user-controlled locations such as Downloads, Documents, Movies, and Desktop. You'll get useful recommendations much sooner, with substantially less risk of harming the system.
If we were to go with a machine learning model, what would I need to build one?

For your macOS disk-cleanup app, I'd build a small supervised machine learning model trained on file metadata and user decisions.

You don't need an LLM, embeddings, or a neural network. This is a classic tabular machine learning problem, and models like logistic regression or gradient-boosted trees are well suited to it.

The biggest challenge is not building the model. It's obtaining the training data.

There are three ways to bootstrap this.

Approach A: Manually labeled dataset. Scan your own machine and a few test machines, have their owners label cleanup candidates, and train a proof-of-concept model. A few hundred examples can validate the pipeline, but won't establish broad accuracy.

Approach B: Heuristic pretraining. Use the macOS cleanup rules from Mole and mac-cleanup-py to generate initial category labels. This can teach a classifier to approximate established rules, but not genuine personal relevance. Don't mistake these synthetic labels for user behavior.

Approach C: Collect actual user feedback. Once your app is usable, capture decisions from its recommendation interface. This is where your most valuable data will come from.

I'd combine A and C, using B primarily for deterministic classification.

Diversity matters more than raw record count. Ten thousand decisions from one developer's Mac would be a poor representation of the general Mac population.

And because users will often approve obvious cleanup candidates, the dataset could be highly imbalanced.

I'd evaluate using precision and recall, plus ranking metrics such as precision@10, rather than accuracy alone. Use time-separated and user-separated test sets so the model isn't merely memorizing one person's cleanup habits.

The most important product metrics would be:

    How often users accept the top recommendations.

    How often users explicitly reject them.

    Whether users restore anything after deletion.

    How much actual storage is recovered.

    Whether recommendations remain useful for new users.

Restoration is a valuable warning signal, but neither restoration nor approval alone proves a recommendation was safe.
7. How I would structure your SQLite databases

I'd maintain two separate SQLite databases.

cleanup_knowledge.sqlite — shipped with the app, containing curated cleanup rules, file categories, and protective rules.

user_relevance.sqlite — stored locally on each Mac, containing file observations, recommendations, and explicit feedback.

The key feedback table could be:

CREATE TABLE file_decisions (
    id INTEGER PRIMARY KEY,
    file_observation_id TEXT NOT NULL,
    decision TEXT NOT NULL,
    model_version TEXT,
    presented_at TEXT NOT NULL,
    decided_at TEXT,
    CHECK (decision IN (
        'keep',
        'delete',
        'skip',
        'restored'
    ))
);

You'd also persist a snapshot of the file's features at the time of recommendation. Otherwise, retraining could accidentally use metadata collected after the user's decision.

One more idea: build a ranking model, not just a classifier

Your actual product goal is not necessarily to identify every irrelevant file.

It's to present the user with the best cleanup opportunities first.

You could eventually rank candidates according to:
U(f)=P(approval∣f)×RecoverableBytes(f)
U(f)=P(approval∣f)×RecoverableBytes(f)

That's a simplified expected-value formulation. You'd still account for deletion risk and the inconvenience of restoring or regenerating files, with hard safety exclusions applied first.

For example, a 4 GB installer with 80% predicted approval might be more valuable to recommend than 100 tiny temporary files with 99% approval.

This changes the ML problem from just classification to a practical recommendation and ranking system.

My recommendation: Build a small Core ML classifier using metadata and explicit user-feedback labels, and keep your SQLite rule database as the independent safety and artifact-classification layer. Your first milestone should be proving that a trained model ranks cleanup candidates better than a simple weighted heuristic.

The question I would investigate next is how to bootstrap a useful model before you've acquired users. That's likely the hardest and most consequential part of the entire design.
